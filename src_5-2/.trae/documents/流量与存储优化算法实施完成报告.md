## 一、项目概述

本项目实现了一套完整的 Modbus 地址段合并与优化算法，旨在减少 4G 模块的上发流量，降低传输成本，同时优化数据存储效率。

### 核心目标
- 最小化 Modbus 数据配置的 payload 大小
- 遵守约束条件（最多 30 个地址段，Zone 1 不超过 1536 位，Zone 4 不超过 12288 个寄存器）
- 完整保留原始变量信息，无数据丢失
- 实现 Go 后端与 Python 参考实现的双版本支持

### 4. 性能优化（关键修复）

#### 4.1 排序算法优化
- **问题**: 多处使用 O(n²) 冒泡排序，处理大量变量时超时
- **解决方案**:
  - 替换所有冒泡排序为标准库 `sort.Slice` 和 `sort.Ints`
  - 复杂度从 O(n²) 降至 O(n log n)
  - 优化位置：
    - `PayloadOptimizer` 各阶段排序
    - `DefaultOptimizer.mergeGroup`
    - `QueryallData` 变量列表排序

#### 4.2 日志输出优化
- **问题**: 大量 INFO 级别日志刷屏，影响性能
- **解决方案**:
  - 将变量遍历日志从 `INFO` 降级到 `DEBUG`
  - 修改 `config.yaml`，日志级别设置为 `info`
  - 保留关键 INFO 日志（优化器执行、阶段耗时等）

#### 4.3 前端超时配置
- **问题**: 5 秒默认超时时间不够优化器执行
- **解决方案**:
  - 修改 `4G_dev_front/4G_dev/src/utils/request.js`
  - 超时时间从 5000ms 增加到 30000ms

### 5. 优化器核心逻辑修复

#### 5.1 extractMustCover 函数优化
- **问题**: 逐个遍历地址，处理大范围地址时容易内存溢出
- **解决方案**:
  - 先收集地址段区间，而不是单个点
  - 合并重叠区间后再展开为单个点
  - 添加安全检查，防止超大地址范围

#### 5.2 buildIntervals 函数修复
- **问题**: K=0 时返回 nil，导致段数为 0
- **解决方案**:
  - 将 K=0 理解为"不合并，全部按单个段处理"
  - 修复 splitIndices 的负数容量问题

## 四、API 接口说明

### 数据配置下发接口
**Endpoint**: `POST /sendcod/data-config`

**请求参数**:
```json
{
  "device_id": "设备ID",
  "variables": ["变量ID列表"]
}
```

**响应示例**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "optimized_payload": "优化后的payload（十六进制）",
    "optimization_result": {
      "original_segments": 原始段数,
      "optimized_segments": 优化后段数,
      "original_payload_size": 原始payload大小（字节）,
      "optimized_payload_size": 优化后payload大小（字节）,
      "savings_bytes": 节省字节数,
      "savings_percent": 节省百分比,
      "execution_time_ms": 执行耗时（毫秒）
    }
  }
}
```
